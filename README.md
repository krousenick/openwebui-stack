## Features

- **Traefik Reverse Proxy**: Automatic HTTPS with self-signed certificates generated by Traefik, HTTP to HTTPS redirect
- **LiteLLM Proxy**: Unified gateway for multiple LLM providers (Gemini, AWS Bedrock, Ollama, local llama.cpp). A built-in content filter runs on every request, and model `auto` routes by prompt complexity.
- **Keycloak Identity Provider**: Single Sign-On (SSO) for all services
- **LGTM Observability Stack**: Grafana, Loki, Tempo, Mimir for logs, traces, and metrics
- **Qdrant Vector Database**: Production-ready vector search for RAG
- **PostgreSQL**: Shared database for Open WebUI, LiteLLM, and Keycloak
- **OpenTelemetry**: Full observability with distributed tracing
- **Security**: Network isolation, secure headers, rate limiting, admin IP restriction
- **Chatterbox TTS**: OpenAI-compatible voice cloning for Open WebUI, with a voice library UI at `voice.<domain>`. This is the only TTS engine in the stack.
- **Brave Search MCP**: Web search for every chat model. The `brave-search-mcp` container serves the official Brave MCP tools over streamable HTTP, LiteLLM mounts them at `/mcp/brave_search`, and a LiteLLM startup hook (`litellm/brave_mcp_callback.py`) injects them into every `/v1/chat/completions` request. Models call the tools; LiteLLM executes them server-side (`require_approval: never`), so no client-side tool wiring is needed.
- **Voice assistant**: LiteLLM alias `voice-assistant` routes to `gemini-3.5-flash-lite` (rendered only when `litellm_gemini_models_enabled: true`, the same flag that gates the Gemini models). `./scripts/create-voice-key.sh` creates a virtual key that can call only that model and stores it in `.env` as `LITELLM_VOICE_API_KEY`.
- **Code Sandbox**: Isolated Jupyter container for model-authored Python (STL/mesh generation, plotting, data transforms). Pinned `quay.io/jupyter/scipy-notebook` image with `numpy-stl` and `trimesh` baked in, token-authenticated, backend-network-only (no published port, no Traefik route), 2G/2CPU caps, non-root. Open WebUI's Jupyter code-execution wiring points at it; the legacy in-process engines stay off. See [Secure Code Execution](#secure-code-execution-code-sandbox).

##  Quick Start

### Prerequisites

- Docker Engine 24.0+
- Docker Compose v2.20+
- 8GB+ RAM recommended
- (Optional) NVIDIA GPU with drivers for GPU metrics

### Installation

1. **Clone the repository**
   ```bash
   git clone https://github.com/mhajder/openwebui-stack.git
   cd openwebui-stack
   ```

2. **Run the setup entrypoint**
   ```bash
   chmod +x scripts/*.sh
   ./scripts/setup.sh
   ```

   `scripts/setup.sh` is a thin wrapper: it installs the Ansible collections (once) and runs `ansible-playbook playbooks/site.yml`. All configuration formerly done by interactive prompts now lives in `ansible/group_vars/all/vars.yml` (domain, TLS mode, compose profiles) and is rendered declaratively:

   - **`.env`** — rendered from `templates/env.j2` with every secret
   - **`docker-compose.yml`** — rendered from `templates/docker-compose.yml.j2`; the `chatterbox_enabled` toggle drops the Chatterbox services entirely
    - **`litellm/config.yaml`** — rendered from `templates/config.yaml.j2` (the Playwright MCP `Host` header needs the deployed domain spelled out; LiteLLM does not expand `${VAR}` in config values). When the rendered content changes, a handler recreates the `litellm` service so the bind-mounted config is reloaded (plain `docker compose up` does not recreate a container for bind-mount content changes)
   - **TLS certificates** — `ssl_cert_type: existing | selfsigned | traefik`; self-signed pairs are generated with `community.crypto` and wired into Traefik via `traefik/dynamic/certs.yml` (replaces `scripts/generate-certs.sh`)
   - **`/etc/hosts`** — service hostnames added on the deployment host for non-localhost domains
   - **Secrets** — explicit values in `ansible/group_vars/all/vault.yml` (tracked template with `CHANGE_ME` placeholders) and `ansible/group_vars/all/vault.local.yml` (real values, gitignored, mode 0600). Nothing reads environment variables or the deployed `.env`. A playbook run fails fast, naming exactly which secrets are still placeholders.

   Edit `ansible/group_vars/all/vars.yml` before the first run to set `domain`, `ssl_cert_type`, `docker_compose_profiles`, and `chatterbox_device`/`chatterbox_enabled`. Copy `vault.yml` to `vault.local.yml`, replace every `CHANGE_ME`, and keep `vault.local.yml` out of git (encrypt it with `ansible-vault` instead for team use).

In `docker-compose.yml` change `ENABLE_SIGNUP` to `true` if you want to register the first admin user via Open WebUI. You can disable it again after the first user is created.

3. **Start the stack**

   The playbook brings the stack up itself (`tasks/compose.yml` applies `docker_compose_profiles`). To run it by hand:
   ```bash
   docker compose --profile monitoring --profile gpu up -d
   ```

4. **Access the services**
   - Open WebUI: https://chatbot.localhost
   - Grafana: https://grafana.localhost
   - LiteLLM: https://litellm.localhost
   - Keycloak (admin): https://auth.localhost/admin
   - Chatterbox voice library: https://voice.localhost

### Complete Reset (retest the playbook from scratch)

`scripts/reset-stack.sh` destroys the deployed stack on the Photon host so the playbook can be validated from a clean slate. It runs `docker compose --profile '*' down -v --remove-orphans`, then sweeps every container, volume, network, and locally-built image carrying the `${COMPOSE_PROJECT_NAME:-openwebui-stack}` prefix (so leftovers the compose file no longer knows about die too), then deletes the deployed tree.

```bash
# On the Photon host, from the repo (or anywhere; the paths are absolute):
bash scripts/reset-stack.sh --dry-run   # show every destructive action first
bash scripts/reset-stack.sh             # wipe stack + /mnt/data1/openwebui-stack
```

Everything in the stack is destroyed: Keycloak users, Open WebUI chats and uploaded files, generated `/models` artifacts, built images. The script only deletes the stack folder itself — everything else under `/mnt/data1` (backups, stashes, old trees, and `/mnt/data1/docker`, which is Docker's data-root) is left alone, and `--dir /mnt/data1` is refused outright. The git checkout and the vault are never touched. After a reset, redeploy with `./scripts/setup.sh`. The script refuses system paths and requires an absolute target with at least two path components; run it as root on the Photon host.

## Keycloak SSO

This stack includes **Keycloak** for centralized authentication (Single Sign-On). All services authenticate through Keycloak instead of using separate credentials.

### Services Integrated with Keycloak

| Service | URL | Client ID | Redirect URI |
|---------|-----|-----------|--------------|
| Open WebUI | https://chatbot.example.com | `open-webui` | `/oauth/oidc/callback` |
| Grafana | https://grafana.example.com | `grafana` | `/login/generic_oauth` |
| LiteLLM | https://litellm.example.com | `litellm` | `/sso/callback` |

### Keycloak Administration

Access the Keycloak Admin Console to manage users and applications:

- **URL**: https://auth.example.com/admin
- **Username**: `admin` (or `KEYCLOAK_ADMIN_USER`)
- **Password**: resolves through the secret tiering (vault entry → environment → deployed `.env` → generated once); see `ansible/group_vars/all/vault.yml`

### First-Time Setup

1. After starting the stack, run the Ansible playbook from `ansible/`:
   ```bash
   ansible-galaxy collection install -r requirements.yaml
   ansible-playbook playbooks/site.yml
   ```
    This creates the `platform` realm, the `keycloak-provisioner` service account, confidential clients for Grafana, Open WebUI, and LiteLLM, client roles that match `docker-compose.yml`, group-to-role mappings, and one login user per group. It also turns on passkeys for that realm: Keycloak shows **Sign in with Passkey** on the username form, and users can register a passwordless credential from the account console. Set `keycloak_passkeys_enabled: false` in `ansible/group_vars/all/vars.yml` to leave password login unchanged. It also syncs `otel/`, `grafana/`, `traefik/`, `json-exporter/`, `litellm/`, and `sandbox/` (minus the rendered `config.yaml`) to `project_root` as mode `0644`, carrying the `always` tag so tag-limited runs (`--tags compose`, `--tags environment`) still sync before `docker compose up`. The collector image runs as uid `10001`, and a `0640` root-owned `otel/config.yaml` makes it crash-loop. The sync builds its rsync from the inventory host's key (`private_key` + `rsync_path: rsync` — the delegate-host defaults offer the agent's identities and inject a sudo wrapper that Photon lacks). Before `docker compose up`, `tasks/compose_mount_check.yml` resolves the deployed compose file and fails the run when a file-kind bind source the checkout has (e.g. a mounted guardrail category file) is missing in the deployed tree: `docker compose` auto-creates missing short-syntax bind sources as empty directories, which the sync cannot replace, so the failure names the exact `rm -rf` to run. Client secrets are the `*_OIDC_CLIENT_SECRET` values the role writes to `.env`; every Keycloak secret (admin password, provisioner client secret, OIDC client secrets, and the `keycloak_user_*` passwords) comes from `vault.local.yml`.

2. Only Grafana, Open WebUI, and LiteLLM use Keycloak. Traefik, Keycloak admin, and the exporters keep their own credentials. `./scripts/setup.sh` runs the playbook for you after installing collections.

3. Optional MCP servers are configured by the playbook through per-server task files in `ansible/roles/openwebui_stack/tasks/mcp/`. Each server is toggled by a variable in `ansible/group_vars/all/vars.yml`, and `tasks/mcp/main.yml` includes only the enabled ones:

   | Variable | Task file | What it configures |
   |----------|-----------|---------------------|
    | `brave_search_enabled` + `brave_search_api_key` (vault) | `mcp/brave.yml` | Open WebUI web search and the `brave_search` tool server connection |
    | `playwright_mcp_enabled` (role default `true`) | `mcp/playwright.yml` | The `playwright_cluster` tool server connection (no secret; containers run from docker-compose.yml) |
    | `playwright_mcp_enabled` (same toggle) | `mcp/tool_image_filter.yml` | The `tool_result_image_display` global outlet filter that promotes MCP tool-result images (Playwright screenshots) to chat message files so they render in the chat window |

   The same toggles also gate the containers and LiteLLM wiring in the compose and config templates, so a toggle off drops every piece at once: `brave_search_enabled` (with a non-empty `brave_search_api_key`) gates the `brave-search-mcp` service, the `mcp_servers.brave_search` entry, and the Brave injector startup hook + callback mount on `litellm`; `playwright_mcp_enabled` gates the `playwright-mcp` service (and its Traefik network alias) and the `mcp_servers.playwright_cluster` entry; `chatterbox_enabled` gates the `oauth2-proxy` voice gate alongside the Chatterbox services and the `VOICE_OIDC_CLIENT_SECRET`/`OAUTH2_PROXY_COOKIE_SECRET` entries in `.env`.

    Both MCP tasks **merge** into the same `tool_server.connections` row (matched by `info.id`, sorted canonically), so each preserves the other's entry, and consecutive playbook runs are idempotent: the litellm and open-webui containers are recreated only when the row actually changes. The tool-image filter task is idempotent the same way (it upserts the `function` row only when content/flags differ, then recreates only `open-webui`).

   Add a future MCP server by dropping `<name>.yml` in `tasks/mcp/`, guarding it in `tasks/mcp/main.yml` with `mcp_<name>_enabled`, and adding that variable to `group_vars/all/vars.yml` and the role defaults.

### Role Mapping

Users are assigned roles based on their Keycloak group membership:

| Keycloak group | Grafana role | Open WebUI role | LiteLLM role | Ansible user |
|----------------|---------------|-----------------|--------------|--------------|
| `platform-admins` | GrafanaAdmin | `openwebui_admin` | `proxy_admin` | `platform-admin` |
| `admin` | Admin | `openwebui_admin` | `proxy_admin` | |
| `editor` | Editor | | | `grafana-editor` |
| `viewer` | Viewer | | | `grafana-viewer` |
| `user` | | `openwebui_user` | `internal_user` | `openwebui-user`, `litellm-user` |
| `litellm-admin` | | | `proxy_admin` | |
| `litellm-viewer` | | | `proxy_admin_viewer` | `litellm-viewer` |

Role names are the values in the `roles` token claim. Grafana maps them with the JMESPath in `docker-compose.yml`. Open WebUI treats `openwebui_admin` as admin. LiteLLM reads `proxy_admin`, `proxy_admin_viewer`, `internal_user`, and `internal_user_viewer` from `GENERIC_USER_ROLE_ATTRIBUTE`.

**Creating more users:**

1. Go to Keycloak Admin Console → Users → Add user
2. Fill in user details and save
3. Go to Credentials tab → Set password (uncheck "Temporary")
4. Go to Groups tab → Join one of the groups in the table

To register a passkey for that user, follow [docs/passkey-user.md](docs/passkey-user.md).

**Realm hardening:** The bootstrap task (`tasks/keycloak_bootstrap.yml`) configures the `platform` realm with brute-force detection (5 failures, 60s→900s wait), a password policy (`length(12) and upperCase(1) and digits(1) and notUsername and notEmail and passwordHistory(5)` — applies to new passwords; existing ones are grandfathered), refresh-token rotation (`revoke_refresh_token` with `refresh_token_max_reuse: 0`, so a replayed refresh token fails immediately after a newer one is issued), and event logging (login events with 30-day retention, admin events with full change payloads). Keycloak 26 hashes with Argon2 by default. See `GET /admin/realms/platform/events` for the event store; the Loki dashboards already have `keycloak_user_events_total` panels for it.

**Self-registration:** The playbook turns on user self-registration for the `platform` realm (`keycloak_registration_enabled` in `ansible/group_vars/all/vars.yml`, default `true` in this deployment; role default `false`). The Keycloak login page shows a **Register** link. New accounts land in `keycloak_default_groups` (here: `user`), so group-to-role mappings grant `openwebui_user` (Open WebUI) and `internal_user` (LiteLLM) immediately — the same access as the provisioned `openwebui-user`. `keycloak_verify_email` is off because no SMTP server is configured: with it on and no mail server, a self-registered user is stuck on the Verify Email screen. Configure SMTP in Keycloak (Realm Settings → Email) and set it to `true` to require address verification. Default groups are set after the groups exist (Keycloak's realm update replaces the whole list and fails on a missing group). Set `keycloak_registration_enabled: false` to hide the Register link again.

**LiteLLM SSO seat limit:** LiteLLM's free tier allows UI SSO for up to 5 users — the 6th sign-up gets a 403 ("SSO for more than 5 users requires a LiteLLM Enterprise license"); existing users always sign in. Open WebUI and Grafana have no such limit. Set `litellm_license` in `vault.local.yml` to a `LITELLM_LICENSE` key (e.g. a trial from [litellm.ai/enterprise](https://www.litellm.ai/enterprise)) to lift it; the playbook renders the env var and compose entry only when a license is set.

### Security Features

Keycloak includes several security hardening options:

- **Admin IP Restriction**: Restrict access to the admin console by IP
  - Set `KEYCLOAK_ADMIN_IP_RANGE` in `.env` (e.g., `10.0.0.0/8`)
  - Default: `0.0.0.0/0` (allow all)

- **Security Headers**: Strict HTTP security headers configured via Traefik

- **Resource Limits**: Memory and CPU limits applied to Keycloak container

### Backups

Keycloak database backups can be run on-demand:
```bash
# Run backup
docker compose --profile backup up keycloak-backup

# List backups (bind mount under the deployed tree, not a Docker volume)
```

### opencode (terminal AI coding agent)

The `opencode` Ansible role installs [OpenCode](https://opencode.ai) on the target host and points it at the stack's LiteLLM proxy, with per-user token accounting. It is a no-op until you list users:

```yaml
# ansible/group_vars/all/vars.yml
opencode_users:
  - username: nicholas.krouse
```

Then run the playbook (tag `opencode` limits the run to this role):

```bash
cd ansible && ansible-playbook playbooks/site.yml --tags opencode
```

Per user, the role:

1. **Installs opencode** globally via npm (`opencode-ai`), installing Node.js first with the OS-appropriate package manager (tdnf on the Photon host, apt/dnf elsewhere) when `opencode_manage_nodejs: true`.
2. **Mints a per-user LiteLLM virtual key** through `POST /key/generate` with the master key from the deployed `.env`, tagging it `key_alias: opencode-<user>`, `user_id: <user>`, and `metadata: {user: <user>, source: opencode}`. Every request opencode makes is then attributed to that user in the LiteLLM UI and `LiteLLM_SpendLogs`, so `/key/list` spend and the Grafana LiteLLM views resolve usage per person without extra headers. The key lands in `~/.config/opencode/litellm.key` (mode 0600); later runs reuse a still-valid key instead of minting again. Optional `models:` on the user entry restricts the key's allowed models, `opencode_key_max_budget`/`opencode_key_rpm` set spend/rate caps.
3. **Auto-discovers models**: the config declares a `litellm` custom provider (`@ai-sdk/openai-compatible`, baseURL `https://litellm.<domain>/v1`) and the [`opencode-plugin-litellm`](https://github.com/yuseferi/opencode-litellm) plugin. The plugin pulls the whole `model_list` from `/v1/models` + `/v1/model/info` (limits, pricing, capability flags) at startup, caches it under `~/.cache/opencode-litellm`, and refreshes in the background — no model list to maintain when you add models to `litellm/config.yaml`. New sessions pick new models up within the 5-minute refresh window. Requires OpenCode ≥ 1.18.29.
4. **Logs local usage**: `~/.config/opencode/plugins/litellm-usage.js` appends one JSON line per assistant message to `~/.local/share/opencode/usage.jsonl` — `user`, `modelID`, input/output/reasoning/cached tokens, cost, and duration — which cross-references the LiteLLM-side spend for the same turns.
5. **Handles the Origin CA**: the proxy serves a Cloudflare Origin certificate, and Node's fetch does not use the system trust store. The role detects the OS: on the Photon host it points `NODE_EXTRA_CA_CERTS` at `certs/origin_ca_rsa_root.pem` in the deployed tree; elsewhere it distributes the public CA root from `ansible/roles/opencode/files/` into `~/.config/opencode/`. Set `opencode_node_ca_cert: false` when the proxy has a publicly trusted cert.

Defaults (`opencode_default_model: litellm/gemini-4-argon`, `small_model: litellm/gemini-3.5-flash-lite`) are set in `ansible/roles/opencode/defaults/main.yml`; any LiteLLM `model_name` works since discovery fills the picker. Run `opencode` and use `/models` to verify the full catalog.

## Web Search (Brave Search MCP)

Every chat model served by LiteLLM can search the web. No per-chat tool setup is required.

### How it works

1. **`brave-search-mcp`** runs the official `mcp/brave-search` image with `BRAVE_SEARCH_API_KEY` and exposes the MCP endpoint over streamable HTTP at `http://brave-search-mcp:8080/mcp` (backend network, no published port).
2. **LiteLLM mounts it as an MCP server** named `brave_search` (`mcp_servers:` in [litellm/config.yaml](litellm/config.yaml)), reachable at `http://litellm:4000/mcp/brave_search`. `allow_all_keys: true` lets any LiteLLM virtual key use it. Eight tools are exposed: `brave_web_search`, `brave_news_search`, `brave_image_search`, `brave_video_search`, `brave_summarizer`, and local search (places, POIs, maps).
3. **A startup hook injects the tools into every non-streaming chat request.** `LITELLM_WORKER_STARTUP_HOOKS: "brave_mcp_callback:register_callback"` loads [litellm/brave_mcp_callback.py](litellm/brave_mcp_callback.py), whose `BraveMCPInjector` is a LiteLLM `CustomLogger`. Its `async_pre_call_hook` appends `{"type": "mcp", "server_url": "litellm_proxy/mcp/brave_search", "require_approval": "never"}` to the `tools` list of every `completion`/`acompletion` call. Streaming requests (`stream: true`) are **skipped**: LiteLLM's MCP streaming iterator forwards the tool-call deltas to the client, and clients with their own function-calling loop (Open WebUI) record those deltas as their own tool calls, fail to resolve the MCP-namespaced name, and append error tool responses that corrupt the history ("Missing corresponding tool call for tool response message" on the next Gemini turn). If the request already carries Brave tools, the hook also skips injection so the model never sees the tool set twice.
4. **LiteLLM executes the tool calls server-side.** With `require_approval: never`, LiteLLM converts the MCP tools to provider function-calling format (Gemini function declarations, Bedrock tools, etc.), runs the call against the Brave MCP container, and sends the results back to the model in a follow-up turn — all inside one `/v1/chat/completions` request. The client only sees the final answer.

Because injection happens in the proxy, it works identically for non-streaming Open WebUI automations, Home Assistant, the voice assistant, and direct `curl` calls: just ask the model to "search the web".

### Web search in streaming chats (Open WebUI)

Streaming chats use the **client-side** MCP path instead, enabled per model with default tool IDs:

1. Open WebUI has a tool server connection of type `mcp` pointing at `http://litellm:4000/mcp/brave_search` (Admin Settings → Tool Servers, bearer auth with `LITELLM_MASTER_KEY`).
2. Each Gemini model has a Workspace entry (Admin → Workspace → Models) with **Default Tools** set to `server:mcp:brave_search`, stored as `meta.toolIds`. The frontend merges this into every chat request's `tool_ids`.
3. Open WebUI resolves the tool server, fetches the 8 tool specs (`brave_search-brave_web_search`, ...), and exposes them to the model as native function tools. The model's tool calls are executed by Open WebUI's MCP client against LiteLLM's MCP gateway.

Verified flow: user asks for weather → model emits a `brave_search_brave_search-brave_web_search` call → Open WebUI calls LiteLLM `/mcp/brave_search` → result returned → final answer with live data. The history stays well-formed (`user → assistant(tool_call) → tool → assistant`), so multi-turn chats never hit "Missing corresponding tool call".

> **Note:** the hook checks `call_type` for both `"completion"` and `"acompletion"`. LiteLLM's `/v1/chat/completions` route invokes `async_pre_call_hook` with `call_type="acompletion"`, so a hook that only matches `"completion"` never fires on real proxy traffic.

### Prerequisites and configuration

- `BRAVE_SEARCH_API_KEY` in `.env` (required; the stack fails to start without it). Free tier: 1 query/second, 2,000/month.
- The `litellm` container mounts `litellm/brave_mcp_callback.py` at `/app/brave_mcp_callback.py` and loads it via `LITELLM_WORKER_STARTUP_HOOKS`.

### Verification

```bash
# 1. Startup hook loaded (litellm logs)
docker compose logs litellm | grep "startup hook"
# ... Worker startup hook 'brave_mcp_callback:register_callback' executed successfully

# 2. A chat request carries the injected mcp tool (check LiteLLM_SpendLogs)
```

### Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| Model says it cannot search the web | Hook did not fire (older callback matched only `call_type="completion"`) | Ensure `litellm/brave_mcp_callback.py` accepts `"acompletion"`; `docker compose restart litellm` |
| "Missing corresponding tool call for tool response message" on Gemini | Streaming request got the injected server-side MCP tool; the client recorded the streamed tool-call deltas as its own and appended error tool responses | Keep `stream` requests excluded in the injector; use the Open WebUI client-side path (Workspace model Default Tools) for streaming chats |

| Tool call fails with "fetch failed" | `brave-search-mcp` outbound call to the Brave API failed (transient) | Retry; check `docker compose logs brave-search-mcp` |
| Tool call fails with 401/403 | Invalid `BRAVE_SEARCH_API_KEY` | Update `.env`, then `docker compose up -d brave-search-mcp` |
| Gemini returns 429 quota errors | Gemini free tier exhausted — unrelated to search tools | Wait for quota reset or set billing on the Gemini project |

Open WebUI's **direct** MCP path (Admin Settings → Tool Servers) is independent: an `mcp`-type tool server connects per-chat via tool IDs (`server:mcp:<id>`) and logs `Initialized 0 tool server(s)` at boot, which is expected for MCP-only configs. The Gemini Workspace models ship with Default Tools set, so streaming chats get web search without per-chat tool selection. Other models (Bedrock, Ollama) get it by adding `server:mcp:brave_search` to their Default Tools, or by picking the tool in the chat composer.

### Default-enabled MCP tools and hidden built-in web search

The playbook configures both MCP tool servers as the **default tools for every model**:

- Open WebUI's built-in web search is **off** (`web.search.enable=false` is set by the Brave task), so the built-in Web Search toggle does not appear for users. Web search happens through the Brave MCP tool server instead, which keeps a single search path (the LiteLLM MCP gateway) for every model.
- The Playbook's `mcp/tool_defaults.yml` writes `models.default_metadata` (`DEFAULT_MODEL_METADATA`) with `toolIds: ["server:mcp:brave_search", "server:mcp:playwright_cluster"]` — restricted to the MCP servers enabled by `brave_search_enabled` / `playwright_mcp_enabled`. Open WebUI fill-only merges this into every model that has no `toolIds` of its own (`get_all_models`), and the frontend merges model `meta.toolIds` into every new chat's selected tools. New chats therefore start with the MCP tools already selected; no per-chat toggle is needed.
- Models with their own Default Tools (the Gemini Workspace models) keep theirs; models that later set their own `toolIds` keep those instead of the global default.
- Turn it off per chat in the chat's tool picker; the default only changes what a new chat starts with.

| Symptom | Cause | Fix |
|---------|-------|-----|
| New chats do not start with the MCP tools | `models.default_metadata` row missing or stale | Rerun the playbook (`ansible-playbook playbooks/site.yml`); verify `SELECT value FROM config WHERE key = 'models.default_metadata'` lists the expected `toolIds` |
| A model never uses the MCP tools | That model has its own `meta.toolIds` set, which replaces the global default | Add the MCP IDs to the model's Default Tools in the Workspace editor |

## Context Compaction

Long chats never die at the context limit again. Every `/v1/chat/completions` request that would exceed the target model's context window is trimmed before it reaches the provider.

### How it works

1. **A startup hook loads the compactor.** `LITELLM_WORKER_STARTUP_HOOKS` includes `context_compaction_callback:register_callback`, which loads [litellm/context_compaction_callback.py](litellm/context_compaction_callback.py). Like the Brave MCP injector, it is a LiteLLM `CustomLogger` whose `async_pre_call_hook` runs on every `completion`/`acompletion` call — streaming included, because trimming never emits tool deltas.
2. **The hook resolves the model's input window** from the live proxy router (`proxy_server.llm_router.get_model_list()` → `model_info.max_input_tokens`, the same field the `vllm_compute` role registers), then LiteLLM's known-model cost map, then a per-model env override (`CONTEXT_COMPACTION_MODEL_<name>`). A model with no resolvable window is left untouched — the provider's own 400 is clearer than a guessed trim.
3. **Oversized histories are trimmed, not summarized.** When the estimated prompt exceeds `window - output_allowance`, the hook keeps every system/developer message, protects up to `CONTEXT_COMPACTION_KEEP_LAST_N` (default 6) newest messages, and drops oldest turns until the rest fits. The retained window is aligned to start at a `user` turn, so assistant tool calls and their tool results are never split apart. A short `[Earlier conversation was compacted...]` note replaces what was dropped, so the model knows older context is missing instead of silently hallucinating around the gap.
4. **The proxy's response is untouched.** Clients (Open WebUI, automations, curl) keep their full local history; only the provider request is trimmed. The trim re-estimates with a 5% safety margin over a 4-chars-per-token floor, so providers do not see borderline prompts.

Turn it off per request with `metadata: {"context_compaction": false}`. Models whose windows are known to the router or the cost map (all registered Gemini/Bedrock/vLLM models here) are handled automatically; register edge-node models with `max_input_tokens` in their LiteLLM entry or set `CONTEXT_COMPACTION_MODEL_<name>`.

## Prompt caching (provider-side, per model family)

LiteLLM's exact-response cache in Valkey is a different feature (see `litellm_settings.cache`); this section is provider-side **prompt caching** — the provider stores the KV state of a repeated prompt prefix and bills reads at a discount. Nothing here needs Redis.

State per model family served through the gateway — the second column is what the mechanism is, the third is what **LiteLLM** can (and cannot) do about it:

| Family / models | Mechanism | LiteLLM-side configuration | State |
|---|---|---|---|
| Anthropic (none deployed yet; any future `anthropic/` or Claude-on-`bedrock/`) | `cache_control` markers (512–4,096 token minimum by model, 4 blocks max, 5m/1h TTL) | `enable_anthropic_prompt_caching: true` in `litellm_settings` — LiteLLM auto-injects one checkpoint on the system prompt and one on the trailing turn; never double-injects when the client sets its own `cache_control` | Enabled gateway-wide; **the only family LiteLLM can inject markers for in this stack** |
| Gemini (`gemini-3.8-flash`, `gemini-3.5-flash-lite`, `gemini-3.1-pro`, `gemini-4-argon`) | Google implicit caching (repeated prefixes, no marker) | **Nothing to enable, and do not add `cache_control_injection_points`**: Gemini 2.5+ caches implicitly for free; markers switch the request to paid explicit context caching with per-object storage billing | Provider-automatic |
| Bedrock OSS (`minimax-m2.5`, `qwen3-next`, `qwen3-coder`, `kimi-k3`) | None — these models are absent from Bedrock's prompt-caching model table ([AWS list](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html#prompt-caching-models)); only Claude/GPT/Nova/DeepSeek on Bedrock cache | Nothing LiteLLM can send that would help; a `cache_control` marker to these models risks a `ValidationException`. `enable_anthropic_prompt_caching` skips them automatically (it is cost-map driven) | N/A (provider doesn't offer it) |
| vLLM compute nodes (`gemma-4-26b-a4b`, aux models) and llama.cpp edge nodes | Server-side KV reuse inside the inference server: vLLM `--enable-prefix-caching` (primary [vllm-serve.sh.j2](ansible/roles/vllm_compute/templates/vllm-serve.sh.j2), aux [vllm-aux.sh.j2](ansible/roles/vllm_compute/templates/vllm-aux.sh.j2)), llama.cpp `--cache-prompt` / `--cache-reuse` ([setup-edge-nodes.sh](scripts/setup-edge-nodes.sh)). Flux image servers have none (image prompts don't repeat prefixes) | **LiteLLM cannot enable this**: these register as `openai/` with a custom `api_base`, and LiteLLM's OpenAI marker mapping only fires against `api.openai.com` hosts — off a custom `api_base` any `cache_control`/breakpoint marker is stripped (a no-op). The caching knob is on the server, already enabled. Prefix hits visible as `vllm:prefix_cache_hits_total` on the Grafana vLLM dashboards | Server-side, enabled (not a LiteLLM knob) |
| Ollama models (`sync-ollama-models.sh`) | Ollama keeps each model's context warm on `localhost:11434` | LiteLLM ignores `cache_control` for `ollama/`; nothing to send. Ollama's own keep-warm behavior applies | Daemon-managed |

How it interacts with the other request rewriters:

- **Context compaction** (above) only fires on oversized histories, and *after* caching the model sees a different retained window — no `cache_control` conflict because LiteLLM's checkpoint injection targets the (system, trailing-turn) shape the compactor preserves.
- **Anthropic checkpoints and Headroom-style compressors** never collide: compressors skip `cache_control`-marked messages by design.
- Open WebUI's long-lived chat sessions are the ideal prompt-cache shape: the system prompt plus all prior turns repeat exactly turn over turn, and only the newest message differs.

Verification: cached reads surface in the response `usage` (`cache_read_input_tokens` on Anthropic shape, `cached_tokens`/`prompt_tokens_details` on OpenAI shape) and per-request in LiteLLM spend logs; vLLM hits on the Grafana `vLLM Remote Nodes` / `vLLM Inference Deployments` dashboards (prefix cache hit% panel); llama.cpp slot reuse in the `/slots` endpoint.

## Secure Code Execution (Code Sandbox)

Chat models can write and run Python (generate STL meshes, plot data, transform files) without ever executing inside the Open WebUI container. Model-authored code runs in the isolated **code-sandbox** service instead. This follows the [Open WebUI hardening guidance](https://docs.openwebui.com/getting-started/advanced-topics/hardening): the legacy in-process engines stay off, and the only code-execution surface is a separate, locked-down Jupyter container.

Open WebUI's workspace Tools still run inside the Open WebUI process — restrict `USER_PERMISSIONS_WORKSPACE_TOOLS_ACCESS` and review every Tool before importing it. The sandbox does not change that; it replaces the *code execution* path.

### How it works

1. **`code-sandbox` container** — a pinned `quay.io/jupyter/scipy-notebook:x86_64-2026-11-02` base ([sandbox/Dockerfile](sandbox/Dockerfile)) plus pinned `numpy-stl` and `trimesh` from [sandbox/requirements.txt](sandbox/requirements.txt) for mesh/STL work. The image builds on the Photon host during the playbook run; nothing installs packages at runtime (`ENABLE_PIP_INSTALL_FRONTMATTER_REQUIREMENTS` stays off for the same reason).
2. **Network isolation** — backend network only (`internal: true`), no published port, no Traefik labels. Nothing outside the Docker backend network can reach the Jupyter API; only the Open WebUI container talks to it at `http://code-sandbox:8888`.
3. **Token auth** — the server requires the `JUPYTER_TOKEN` from vault (`code_sandbox_token` in `ansible/group_vars/all/vault.local.yml`); Open WebUI sends it via `CODE_EXECUTION_JUPYTER_AUTH: token`. Unauthenticated requests get `403`. [sandbox/jupyter_server_config.py](sandbox/jupyter_server_config.py) also disables the terminal server and culls idle kernels after 5 minutes (busy after 10).
4. **Resource limits** — `deploy.resources.limits` cap the container at 2G RAM / 2 CPUs; a runaway kernel cannot starve the host. The container runs as `jovyan` (uid 1000), non-root, with `no-new-privileges`.
5. **Wiring is healed by the playbook** — Open WebUI persists code-execution settings in its DB after first boot, so [tasks/code_sandbox.yml](ansible/roles/openwebui_stack/tasks/code_sandbox.yml) asserts the intended values (`code_execution.engine: jupyter`, `code_execution.jupyter.url: http://code-sandbox:8888`, auth `token`, 120s timeout) on every run and heals drift, the same way `openwebui_config.yml` heals the OpenAI connection. `ENABLE_CODE_EXECUTION` / `ENABLE_CODE_INTERPRETER` stay `false` — the legacy pyodide/jupyter in-process engines never run.
6. **Toggle** — `code_sandbox_enabled: true` in [ansible/group_vars/all/vars.yml](ansible/group_vars/all/vars.yml). Set `false` to drop the container and wiring entirely; the playbook renders the services out of the compose file.

Artifacts (the generated STL) land in the `code_sandbox_data` volume mounted at `/home/jovyan/work`; kernels are per-request and culled when idle.

> **Why quay.io:** Docker Hub's `jupyter/scipy-notebook` mirror stopped updating years ago; the current daily tags live on [quay.io/jupyter/scipy-notebook](https://quay.io/repository/jupyter/scipy-notebook). When rebuilding, pick the newest `x86_64-<date>` tag.

| Symptom | Cause | Fix |
|---------|-------|-----|

## Browser Automation (Playwright MCP cluster)

Chat models can drive a real headless Chromium through the official [Playwright MCP server](https://github.com/microsoft/playwright-mcp). The stack runs five replicas (`deploy.replicas: 5`) behind Traefik so multiple users get parallel browser sessions.

### How it works

1. **Five `playwright-mcp` replicas** run `mcr.microsoft.com/playwright/mcp` (headless Chromium, `pdf` and `devtools` capabilities) on the backend and frontend networks, port 8931. The service has no `container_name`: Compose rejects `container_name` together with `replicas` because replica names must be unique.
2. **Traefik load-balances across the replicas.** The `playwright` router matches `Host(playwright-mcp.${DOMAIN})` on the dedicated `mcp` entrypoint (`:8082`), not `web` — `web` 308-redirects every request to `websecure`, and LiteLLM's MCP client (httpx) does not follow redirects.
3. **Sticky cookies keep MCP sessions working.** Playwright MCP keeps each streamable-HTTP session (`mcp-session-id`) in the replica process's memory. Round-robin routing sends follow-up calls to replicas that never saw the `initialize` and they answer `404 Session not found`. The `playwright` service sets `loadbalancer.sticky.cookie=true` (cookie `pwsticky`), so Traefik pins all requests of one session to the replica that owns it. LiteLLM's MCP client reuses Traefik's `Set-Cookie` automatically (httpx cookie jar), so no client-side wiring is needed.
4. **`PLAYWRIGHT_MCP_ALLOWED_HOSTS: "*"` passes the Host check.** The server enforces a Host allowlist (DNS-rebinding protection) that only contains `localhost:8931` by default. Traefik forwards the incoming `Host: playwright-mcp.<domain>` header, which would get a `403 Access is only allowed at localhost:8931` without the wildcard.
5. **LiteLLM mounts it as `playwright_cluster`** (`mcp_servers:` in [litellm/config.yaml](litellm/config.yaml)) with `url: http://traefik:8082/mcp`, a `Host` header matching the router rule, and `allow_all_keys`-style open access. Tools are exposed with the `playwright_cluster-` prefix (for example `playwright_cluster-browser_navigate`).
6. **Screenshots render in the chat window** through the `tool_result_image_display` global filter. Open WebUI 0.13.0 stores MCP image results only on the `function_call_output` output item's `files` array, which the frontend renders solely inside the collapsed "Tool Executed" box; the message node's own `files` array stays empty, so `browser_take_screenshot` images never appeared in the chat (the [open-webui#33320](https://github.com/open-webui/open-webui/issues/33320) class of bug). The filter — a global outlet filter (functions must expose a `Filter` class in 0.13.0; the loader rejects module-level handlers) registered by `mcp/tool_image_filter.yml` from `roles/openwebui_stack/files/functions/tool_result_image_display.py` — re-emits the tool image URLs through the socket `files` event after each turn, which persists them onto the assistant message node and pushes them to the frontend, where the chat bubble renders them like any attached image. No request or response content is modified. The task recreates only the `open-webui` service (with `build: never`, so a compose file referencing unpublished local images cannot break the recreate) and is idempotent.

Scaling up or down: change `deploy.replicas` in `docker-compose.yml`, then `docker compose up -d playwright-mcp`. Existing sessions stay pinned to their replica via the sticky cookie; a new `initialize` lands on whichever replica Traefik picks next.

### Verification

```bash

docker compose ps playwright-mcp

# 2. Traefik has every replica behind the playwright service (sticky cookie set)
curl -s http://traefik:8080/api/http/services -H "Authorization: Basic ..." | \
  jq '.[] | select(.name | startswith("playwright")) | {name, status, servers: [.loadBalancer.servers[].url]}'

# 3. End-to-end through the load balancer: initialize, then reuse the session
curl -sD /tmp/h -X POST http://traefik:8082/mcp \
  -H "Host: playwright-mcp.localhost" -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"t","version":"1"}}}'
# Mcp-Session-Id header present + Set-Cookie: pwsticky=... -> session created and pinned

curl -s -X POST http://traefik:8082/mcp -b "pwsticky=<cookie>" \
  -H "Host: playwright-mcp.localhost" -H "Mcp-Session-Id: <id>" \
  -H "Accept: application/json, text/event-stream" -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list"}'   # HTTP 200, not 404
```

### Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| `404 Session not found` on follow-up tool calls | Sticky cookies disabled or cookie not sent | Keep `loadbalancer.sticky.cookie=true`; verify `Set-Cookie: pwsticky` on `initialize` |
| `403 Access is only allowed at localhost:8931` | Server Host allowlist rejects the forwarded Host | Keep `PLAYWRIGHT_MCP_ALLOWED_HOSTS: "*"` |
| `can't set container_name ... must be unique: invalid compose project` | `container_name` left on the replicas service | Remove `container_name` from `playwright-mcp` |
| LiteLLM gets `301/308` or connection errors on the MCP server | URL points at the redirecting `web` entrypoint | Use `http://traefik:8082/mcp` (the `mcp` entrypoint) |
| Compose cannot resolve `traefik` from litellm | Services not sharing a network | `litellm` and `traefik` both attach to `frontend` |
| Tool screenshots missing from the chat window (only in the "Tool Executed" box) | `tool_result_image_display` filter missing, disabled, or failed to load (0.13.0 requires a `Filter` class; the loader also auto-disables a function that fails to compile) | Rerun the playbook (or `ansible-playbook playbooks/tool_image_filter.yml` for just this fix); check `SELECT is_active FROM function WHERE id = 'tool_result_image_display'` |
| `Error loading module: tool_result_image_display: No Function class found` in Open WebUI logs | Filter source written with a module-level `outlet` function | Handlers must be methods of a `class Filter` in 0.13.0; redeploy after fixing |

## Centralized Skills (Skills Gateway)

Reusable agent know-how lives in `skills/<name>/SKILL.md` (Claude/Anthropic
Agent Skills format, agentskills.io). One checkout, three consumers:

| Skill | What it teaches |
|---|---|
| `3d-print-pipeline` | Prompt-to-print on the Bambu H2C (tool map, `/models`, mm checks, ask-before-print) |
| `stack-ops` | Operating this stack: playbook re-runs, health checks, SpendLogs/guardrail/MCP diagnostics, Photon host layout |
| `sso-troubleshooting` | Keycloak OIDC failures across Open WebUI/LiteLLM/Grafana: symptom → cause → fix |
| `guardrail-tuning` | Editing the content-filter category overrides without losing injection defenses |
| `web-search-verify` | End-to-end Brave MCP verification: container, startup hook, injected tools, streaming path |

### How it works

Each `skills/<name>/SKILL.md` (frontmatter `name` must match the directory,
`description` drives discovery) is published to three places by the
playbook — no MCP server needs to be enabled, skills are plain
instructions:

1. **LiteLLM proxy skill store** (`tasks/mcp/skills_gateway.yml`): the
   zip is uploaded to `POST /v1/skills` with `custom_llm_provider=
   litellm_proxy`, persisted in the proxy's Postgres. The
   `/.well-known/agent-skills/index.json` discovery index lists every
   stored skill with its archive sha256 (`litellm_settings.
   public_skills_index: true`, rendered from `templates/config.yaml.j2`,
   toggle `skills_public_index_enabled`). Idempotent: the task recomputes
   the deterministic archive digest of the checkout's SKILL.md and only
   deletes + re-uploads on drift (the store has no update endpoint).
2. **Claude Code marketplace**: a registry entry per skill
   (`POST`/`PUT /claude-code/plugins/<name>`), its archive source pointing
   at the proxy's own `https://litellm.<domain>/v1/skills/<id>/archive` —
   nothing leaves the network. Sources must be https, hence the public URL.
3. **Open WebUI workspace** (`tasks/openwebui_skills.yml`): the playbook
   pushes each SKILL.md through Open WebUI's Skills API
   (`/api/v1/skills/create` + `/id/<name>/update` with
   `expected_version_id`) using a dedicated `skill-publisher` admin API
   key (`openwebui_api_admin_key` in the vault). Skills then appear in
   Workspace → Skills for everyone; bind them to models or `$`-mention
   them per chat. Idempotent: unchanged content is skipped.
4. **opencode** (optional, `opencode_sync_skills: true` in the opencode
   role): the playbook copies `skills/*` into each user's global
   `~/.config/opencode/skills/`, where opencode discovers them through its
   native `skill` tool.

Semantic skill search ranks the proxy store on demand
(`skill_search_embedding_model: text-embedding` → gemini-embedding-001,
needs `litellm_gemini_models_enabled: true`).

## 3D Print Pipeline (Blender / FreeCAD / printer MCP)

Prompt-to-print: the chat model authors geometry (Blender mesh or FreeCAD
parametric CAD), exports a verified STL to a shared volume, slices it with
Bambu Studio, and starts the print on the Bambu H2C — asking first. Full
design rationale: `docs/plans/3d-print-pipeline.md`. Model prompt rules:
`docs/3d-print-pipeline-prompt.md`.

### How it works

Three first-class MCP tool servers, all behind LiteLLM (`/mcp/<name>`) so
streaming chats and server-side injection share one gateway:

- **`printer_3d`** (`printer-mcp` container, built from `./printer-mcp`):
  `bambu-printer-mcp@1.1.59` (the Bambu-only fork; its parent
  `mcp-3D-printer-server` is slicing-only for the H2C) + the extracted
  Bambu Studio `v02.08.02.60` CLI (first stable line with H2C machine
  presets) + ffmpeg for RTSP camera snapshots. Tools: `slice_stl`,
  `print_3mf`, `process_and_print_stl`, `get_printer_status`,
  `resolve_3mf_ams_slots` (dry-run filament plan), `camera_snapshot`.
  Sits on `frontend` **and** `backend`: it needs LAN egress to the printer
  (MQTT 8883, FTPS 990, RTSP 322), and `backend` is internal-only.
- **`blender`** (`blender` container, built from `./blender`): Blender 5.0.1
  running as a full GUI under **Xvfb** — the mcp-for-blender addon's
  auto-start refuses background mode (`bpy.app.background`), so a real event
  loop is required — with the mcp-for-blender 2.2.7 addon
  (`BLENDER_MCP_SAFE_MODE=1`). The addon listener (`:9876`) is unauthenticated
  Python execution by design, so the container is backend-only with no
  internet; its only client is the in-container stdio server, bridged to
  streamable HTTP `:8000/mcp` by supergateway for LiteLLM.
- **`freecad`** (`freecad` container, built from `./freecad`): FreeCAD 1.1.4
  AppImage extracted to `/opt/freecad` (bundled py311 `freecadcmd`), the
  alosslessdev headless XML-RPC bridge (`headless_server.py`, commit
  `6f0b530`, freecad-mcp `0.1.24` — the PyPI `0.1.28` is upstream's and
  would handshake-warn against the fork's addon), and supergateway
  stdio→streamable-HTTP `:8000/mcp`. No GUI, no display, no docker socket.
  The XML-RPC bridge (`:9875`) is unauthenticated: backend-only.

A shared named volume `models` is mounted at `/models`: writable in
`blender`, `freecad`, and `code-sandbox` (trimesh post-processing), read-only
in `printer-mcp` (the slicer only ever reads STLs from it).

**Agent behavior lives in the LiteLLM Skills Gateway.** The 3D-print
skill is a Claude/Anthropic Agent Skills package at
`skills/3d-print-pipeline/SKILL.md` (tool map, `/models` convention, mm
dimension check, ask-before-print rule). It is registered by the same
Skills Gateway flow as every other skill in `skills/` — see
[Centralized Skills](#centralized-skills-skills-gateway). Semantic skill
search ranks it on demand (`litellm_settings.skill_search_embedding_model:
text-embedding` → gemini-embedding-001), so agents describe what they need
instead of listing the registry.

**Open WebUI** gets the skill the same way as the rest of `skills/` — the
playbook pushes it into the workspace through the Open WebUI Skills
API (`ansible/roles/openwebui_stack/tasks/openwebui_skills.yml`), after
which you can bind it to models (Workspace → Models → Skills row) or
`$`-mention it per chat. **The ask-before-print rule travels with the
skill text in every store.**

### Downloading generated files from chat

Files the pipeline exports to `/models` are downloadable directly from the
chat window. Open WebUI only persists image/audio tool results as real
files; binary CAD output would otherwise stay an unreadable path in tool
text. Two pieces close that gap (both playbook-managed):

1. `open-webui` mounts the shared `models` volume **read-only** (compose
   template, whenever any 3D-pipeline service is enabled).
2. The `tool_result_file_download` global outlet filter
   (`ansible/roles/openwebui_stack/files/functions/tool_result_file_download.py`,
   published by `tasks/mcp/tool_file_filter.yml`) scans the finished
   assistant turn for `/models/**.stl|3mf|step|stp` mentions in tool
   results, reads each file from the read-only mount, uploads it through
   Open WebUI's own upload handler (normal ownership/storage rules apply),
   and emits a files event so the message renders a file card. Clicking
   the card opens the file modal with a download link
   (`/api/v1/files/<id>/content`, session-authenticated, served with
   `Content-Disposition: attachment`).

Verified end-to-end in the browser: a chat that exports
`/models/ui-e2e-cube.stl` ends with a `ui-e2e-cube.stl 684.0 B` card on
the assistant message whose link returns the binary STL.

### Enabling

1. Printer: touchscreen **Settings → Network → LAN Only Mode + Developer
   Mode**. Developer Mode off makes the firmware refuse remote starts
   (HMS `0500-0500-0001-0007`).
2. Vault (`ansible/group_vars/all/vault.local.yml`, gitignored): set
   `bambu_host` (printer IP), `bambu_serial` (Settings → Device Info),
   `bambu_token` (LAN access code). Never paste these in chat. They follow
   the same var tiering as the rest of the stack, so `-e` extra-vars can
   override them per-run if you prefer not persisting them.
3. Toggles (`ansible/group_vars/all/vars.yml`): `printer_mcp_enabled: true`,
   `blender_mcp_enabled: true`, `freecad_mcp_enabled: true`. Optional:
   `printer_mcp_bed_type` (default `textured_plate` — `supertack_plate` is
   not verified through the CLI) and `printer_mcp_nozzle_diameter`.
 4. `cd ansible && ansible-playbook playbooks/site.yml` — builds the three
    images on the Photon host, renders compose/env/config, merges the
    Open WebUI `tool_server.connections` plus global default tool IDs, and
    registers the `3d-print-pipeline` skill through the Centralized Skills
    flow (proxy skill store, Claude Code marketplace, Open WebUI workspace).

### Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| `printer-mcp` up, `get_printer_status` times out | Printer unreachable or wrong serial/access code | Verify LAN Only + Developer Mode, `bambu_host`/`bambu_serial`/`bambu_token` in vault.local.yml; ping the printer from the Photon host |
| Print starts refused, HMS `0500-0500-0001-0007` | Developer Mode disabled | Enable on the touchscreen; `clear_hms_errors` via the server |
| `slice_stl` fails: profile/bed errors | Wrong machine preset or bed | Keep `BAMBU_MODEL=h2c`; use `textured_plate` (CLI path unverified for `supertack_plate`) |
| `slice_stl` fails: wrong bed/machine never heard of H2C | Bambu Studio older than the presets | The image pins `v02.08.02.60`; do not downgrade below `v02.05.01.52` (first with H2C presets) |
| `blender` unhealthy / `:9876` dead | Blender started in background mode, or Xvfb missing | The image runs full GUI under Xvfb (start.sh); check `docker compose logs blender` for Xvfb or addon auto-start errors |
| `blender` tools time out but container healthy | First boot: Blender GUI + addon auto-start race | Wait out the `start_period: 60s`; retry the tool call |
| LiteLLM cannot reach `blender`/`freecad` MCP | supergateway not up yet | `docker compose logs blender freecad` — the entrypoints wait for the backend (:9876 / :9875) before starting the gateway |
| `freecad` tools warn about addon version mismatch | MCP server installed from PyPI (0.1.28) instead of the fork (0.1.24) | Rebuild the image; the Dockerfile pins the fork commit for both sides of the handshake |
| `export_mesh.stl` / `export_scene.stl` "could not be found" in Blender code | Blender 5.x ships STL I/O as the builtin `bpy.ops.wm.stl_export(filepath=...)` (and `wm.stl_import`); the legacy `export_mesh.stl` operator no longer exists | Use `bpy.ops.wm.stl_export`; note SAFE_MODE also rejects `import os` and `dir()` in exported scripts — print markers instead |
| STL/STEP export fails "Permission denied" or "Cannot open file" under `/models` while containers are healthy | The `models` volume is created root-owned by the local driver; `blender`/`freecad`/`code-sandbox` all write as uid 1000 | The playbook chowns the volume mountpoint to 1000:1000 (`tasks/mcp/models_volume.yml`); rerun the playbook after recreating the volume |
| Open WebUI shows `server:mcp:printer_3d` tools as dead | Server toggled off but old tool defaults remain | Toggle off in vars.yml and rerun the playbook (tool_defaults rebuilds from the enabled set) |
| Model starts prints without asking | Prompt rules not attached | Add `docs/3d-print-pipeline-prompt.md` to the model's system prompt; the server gate does not ask |
| Non-streaming chat with client-side MCP tools returns "Error executing tool: `blender_blender-...`" (LiteLLM KeyError) | The Brave MCP injector added an `mcp`-type tool to a request that already carried Open WebUI's client-side function tools; one `mcp` tool flips LiteLLM into gateway auto-execution for every tool call in the turn | The injector skips any request with function-type tools (`litellm/brave_mcp_callback.py`); rerun the playbook to sync it |
| Exported STL/3MF has no file card in the chat | Outlet filter not active, or the `models:ro` mount missing on `open-webui` | Rerun the playbook; the mount renders whenever a 3D-pipeline service is enabled and `tasks/mcp/tool_file_filter.yml` upserts the filter |

## Local models

Open WebUI does not talk to Ollama or llama.cpp directly (`ENABLE_OLLAMA_API` is `false`). It uses LiteLLM. Register local models on LiteLLM and they show up in the chat UI.

### llama.cpp edge nodes

Use this for GGUF models served by `llama-server` (typically a Fedora host with an NVIDIA GPU). Run `./scripts/setup-edge-nodes.sh` for the interactive node wizard; it writes `LLAMA_CPP_EDGE_NODES` to the deployed `.env`.

1. **Configure the nodes**
   ```bash
   ./scripts/setup-edge-nodes.sh
   ```
   The script asks for each node's hostname or IP, port (default `8080`), and model name, then GPU layers, context size, parallel slots, the model directory (default `/opt/models`), and the `llama-server` path. Current `llama-server` takes parallel slots as `--parallel` (`-np`), not `--slots`. If a generated unit fails to start, change `--slots` to `--parallel` in that unit. Flag list: [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).

2. **What it writes**
   - `LLAMA_CPP_EDGE_NODES` in `.env` (`host:port`, comma-separated)
   - `edge-nodes/llama-server.service` plus one unit per node
   - `edge-nodes/setup-edge-node.sh` (installs llama.cpp with CUDA and enables the systemd unit)
   - `edge-nodes/monitor-edge-nodes.sh`
   - A LiteLLM `model_list` snippet printed at the end

3. **Install each edge node**
   Copy `edge-nodes/setup-edge-node.sh` and that node's `llama-server-*.service` to the machine, then run the setup script there (it needs `sudo`). Put the GGUF at `/opt/models/<model-name>.gguf`. The generated unit expects that filename.

4. **Register the model in LiteLLM**

   Add the snippet the script printed to `model_list` in [litellm/config.yaml](litellm/config.yaml). llama.cpp's OpenAI-compatible API is `http://<host>:<port>/v1`. LiteLLM's OpenAI provider rejects the call without `api_key`, so the snippet uses `local`. `max_input_tokens` and `max_tokens` match the server context. Start `llama-server` with `-c` at least that large:

   ```yaml
   - model_name: llama-3.1-8b-instruct
     litellm_params:
       model: openai/llama-3.1-8b-instruct
       api_base: http://192.0.2.10:8080/v1
     model_info:
       description: "llama-3.1-8b-instruct on 192.0.2.10"
   ```

5. **Reload LiteLLM and check the node**
   ```bash
   docker compose restart litellm
   ./edge-nodes/monitor-edge-nodes.sh
   ```
   The monitor script reads `LLAMA_CPP_EDGE_NODES` and checks `http://<host>:<port>/health`. In Open WebUI the model name is the `model_name` you set (for example `llama-3.1-8b-instruct`).

### vLLM distributed inference compute nodes

For full HF-precision models larger than a single llama.cpp node can serve, use the `vllm_compute` Ansible role. It deploys the official `vllm/vllm-openai` container onto Fedora compute nodes connected over 10/25GbE, driven by Docker **or podman** (`vllm_container_cli`), with two distributed modes. Full reference — architecture, all parallelism modes, variable reference, setup and operations: [docs/vllm-inference.md](docs/vllm-inference.md).

- **Pipeline parallelism (`vllm_deployment_mode: ray`, default)**: one Ray head + workers, one `vllm serve` on the head. `--pipeline-parallel-size` defaults to the node count; each node serves a contiguous layer range. Fits the 10GbE fabric because PP transfers activations only at stage boundaries.
- **Cross-node tensor parallelism**: set `vllm_cross_node_tensor_parallel: true`. Spreads TP across the cluster (`TP = tensor_parallel_size × nodes`). Verify the fabric can sustain it (25GbE+ recommended); 10GbE will bottleneck NCCL all-reduce.
- **Standalone replicas (`vllm_deployment_mode: standalone`)**: every node runs the full model independently; LiteLLM load balances across endpoints. No cross-node traffic at all.
- **Reasoning models**: set `vllm_reasoning_parser` (e.g. `gemma4`, `qwen3`, `deepseek_r1`) on the primary or a `reasoning_parser` key on an aux entry. The role renders `--reasoning-parser` so vLLM returns the trace in a separate `reasoning` field, optionally `--default-chat-template-kwargs` for thinking defaults (`vllm_chat_template_kwargs`, e.g. `{thinking: true}` for Gemma 4), and the LiteLLM registration carries `supports_reasoning: true`. Parser names per model series: [vLLM reasoning docs](https://docs.vllm.ai/en/stable/features/reasoning_outputs.html). Thinking **level** is per-request (`reasoning_effort`, settable from Open WebUI's Advanced Params and MAGIE's thinking selector); set `vllm_reasoning_effort` for the LiteLLM-side default. Details: [docs/vllm-inference.md](docs/vllm-inference.md).

1. **Inventory**: add your nodes under `vllm_compute` in `ansible/inventory/hosts.yml` and mark exactly one host `vllm_ray_head: true` for ray mode.
2. **Configure**: edit `ansible/group_vars/vllm_compute/vars.yml` (model, GPUs per node, pipeline size, firewall CIDR, `VLLM_API_KEY`).
3. **Deploy**:
   ```bash
   cd ansible
   ansible-galaxy collection install -r requirements.yaml
   ansible-playbook playbooks/inference.yml
   ```
     The role runs after the global `prerequisites` role, which checks the container CLI (Docker + compose, or podman) and — for this group via `prerequisites_check_nvidia: true` in `ansible/group_vars/vllm_compute/vars.yml` — the NVIDIA driver. Set `prerequisites_install_missing: true` for a node group and the role installs the missing CLI plus the NVIDIA container toolkit and generates the CDI spec podman's `--device nvidia.com/gpu=all` consumes; with the default `false` it fails fast with install guidance instead. The role opens pinned Ray ports (6379, 8265, 13377-13379, 14000-15000) in a dedicated `vllm-cluster` firewalld zone restricted to the compute CIDR (via the `ansible.posix.firewalld` module, which also admits SSH so the management subnet keeps shell access), deploys systemd units (`vllm-ray`, `vllm-serve`), waits for Ray workers to join, then waits for `GET /health` on the API.
4. **Register with LiteLLM**: the run renders `litellm/vllm-models.yaml` with the `model_list` snippet (single cluster endpoint in ray mode; one entry per node in standalone mode). Merge it into `litellm/config.yaml` on the photon host and `docker compose restart litellm`.

#### Flux image-generation servers

The `vllm-flux` container was removed from `docker-compose.yml`; the `vllm_compute` role now deploys Flux as systemd services on the compute nodes. Set `vllm_flux_enabled: true` and list models in `ansible/group_vars/vllm_compute/vars.yml`:

```yaml
vllm_flux_models:
  - name: flux
    model: black-forest-labs/FLUX.1-dev
    port: 8005
  - name: flux-schnell
    model: black-forest-labs/FLUX.1-schnell
    port: 8006
```

Each entry gets its own `vllm-flux-<name>` systemd unit, launch script, and host port; removing an entry from the list removes its unit and script. Per-entry keys (`name`, `model`, `port`, `tensor_parallel_size`, `max_model_len`, `gpu_memory_utilization`, `extra_args`) override the `vllm_flux_default_*` role defaults, so a bare `- model: <repo-id>` entry runs the fleet defaults. Flux model entries appear in `litellm/vllm-models.yaml` with `mode: image_generation`; merge them into `litellm/config.yaml` and `docker compose restart litellm`. Details: [docs/vllm-inference.md](docs/vllm-inference.md).

#### Aux model servers (per-node placement)

For running additional models on specific compute nodes — e.g. a vision-language model for deep event analysis on the node with the big GPU and a tiny 0.6B true/false decider spread across the fleet — the role places **aux model servers**: `vllm_aux_enabled: true` plus a `vllm_aux_models` list whose entries carry a `hosts` key selecting the nodes:

```yaml
vllm_aux_models:
  - name: vision-analyst
    model: Qwen/Qwen3.5-VL-8B
    hosts: [vllm-node-01]
  - name: gatekeeper
    model: Qwen/Qwen3-0.6B
    hosts: all
```

Each entry deploys one standalone `vllm serve` with its own `vllm-aux-<name>` systemd unit and host port (default base 8010) on the selected nodes only. Per-entry keys are the flux keys plus `hosts` (list, comma string, or `all`), `api_key`, `reasoning_parser`, and `chat_template_kwargs`; removing an entry or a host cleans up automatically. Each (node, entry) placement renders a `model_list` entry into `litellm/vllm-models.yaml` — a model placed on several nodes appears under the same `model_name` and LiteLLM load balances the replicas. Details: [docs/vllm-inference.md](docs/vllm-inference.md).

Ray traffic is unauthenticated and can execute arbitrary code; keep `vllm_firewall_zone_source` limited to the compute segment and set `VLLM_API_KEY` on the controller so the API requires auth. The zone's source binding routes all traffic from that subnet into the zone, so the role also admits the `ssh` service there — without it, management hosts in the subnet lose SSH to the node when the zone reloads.

#### Remote node monitoring

The role deploys Prometheus exporters on every compute node (`vllm_monitoring_enabled`, default on): **node-exporter** (host metrics, port 9100) and the **flavor-correct GPU exporter** — dcgm-exporter (9400) for datacenter GPUs, the nvidia-smi exporter (9835) for GeForce cards, auto-detected via `nvidia-smi`. Ports already served by host rpms are reused, not double-deployed. Podman nodes run them as systemd quadlets, docker nodes via `docker_container` restart policy. The role injects inventory-templated scrape jobs into `otel/config.yaml` (GPU job, `remote-node`, `remote-vllm`), and templates a `vLLM Remote Nodes` Grafana dashboard into `grafana/provisioning/dashboards/json/` whose GPU panels query both DCGM and nvidia_smi metric families. The run also registers the served model with LiteLLM directly (`POST /model/new`, needs `LITELLM_MASTER_KEY` on the controller) — no litellm restart needed. After a run, `docker compose --profile monitoring restart otel-collector lgtm` picks up new scrape jobs and the dashboard. Hardware firewall: allow management → node TCP 9100, 9400 (or 9835 for GeForce nodes), 8000.

**vLLM log shipping** (`vllm_log_shipping_enabled`, default on): the `vllm-serve` systemd unit runs podman without detached logs, so vLLM output lands in journald. Each node runs a `vllm-log-shipper.service` unit (Grafana Alloy container, `/opt/vllm/vllm-log-shipper.alloy`) that reads `vllm-serve.service` journal entries (`loki.source.journal`) and pushes them to the controller's Loki push API (`vllm_loki_push_url`, built from `vllm_controller_host` + `vllm_loki_push_port`; the controller host resolves from the `openwebui` inventory group's `ansible_host`, with an explicit override for inventories that define only `vllm_compute`). The controller publishes the lgtm service's port 3100 on `STACK_HOST_IP` (`.env`, rendered from `ansible_default_ipv4`) — Docker's DNAT routes inbound traffic past the host's INPUT-chain firewall, the same mechanism Traefik's 443 uses. In Grafana the logs carry `service_name`/`container_name` = `vllm-serve` plus a per-node `node` label; the `vLLM Remote Nodes` dashboard has a **vLLM Serve Logs** panel with a `log_filter` textbox variable. Node clocks must be NTP-synced: Loki rejects entries stamped outside its acceptance window ("timestamp too new" / "entry too far behind").

### Sync Ollama models

There is no `sync-llama-models` script. `./scripts/sync-ollama-models.sh` registers models that are already installed in Ollama with the LiteLLM proxy. It does not pull models, start Ollama, edit `litellm/config.yaml`, or restart containers. LiteLLM has `store_model_in_db` enabled, so each new model is stored through `POST /model/new` and is available without a restart. Open WebUI then lists it under the registered name.

The script is interactive and takes no arguments. It asks for the four values below, prints them back (the master key is truncated), and waits for `y` before it changes anything.

```bash
./scripts/sync-ollama-models.sh
```

| Prompt | What to enter |
|--------|----------------|
| Ollama public URL | Where **this script** can reach Ollama. Used only for `GET /api/tags`. Default `http://localhost:11434`. |
| Ollama internal URL | Where the **LiteLLM container** can reach Ollama. Saved as `api_base` on each model. Default `http://host.docker.internal:11434` (Docker Desktop and OrbStack). On Linux Engine, use an address that resolves inside the container. `localhost` here points at the LiteLLM container, not the host. |
| LiteLLM API URL | Where this script can reach the proxy. Default `https://litellm.localhost`. TLS verification is disabled (`curl -k`) so the stack's self-signed cert works. |
| LiteLLM master key | `LITELLM_MASTER_KEY` from `.env`. Required. Sent as `Authorization: Bearer`. |

What it does, in order:

1. `GET <ollama public URL>/api/tags` and read each `.models[].name`. `jq` is used when it is installed; otherwise the script extracts `"name"` fields itself. It exits if Ollama cannot be reached or the response has no models.
2. `GET <LiteLLM URL>/models` and collect existing model ids. If that call fails, it warns and continues with an empty list, so it will try to add every Ollama model.
3. For each Ollama model not already registered as `ollama/<name>`, `POST <LiteLLM URL>/model/new` with:

```json
{
  "model_name": "ollama/llama3.1:8b",
  "litellm_params": {
    "model": "ollama/llama3.1:8b",
    "api_base": "http://host.docker.internal:11434"
  }
}
```

`ollama/` is the LiteLLM provider prefix. `api_base` is the Ollama root (no `/v1`). A model whose id is already `ollama/<name>` is skipped, not updated. The script does not delete LiteLLM entries that you later remove from Ollama.

It prints successful, skipped, and failed counts. Exit code is `0` when nothing failed (including a `n` at the confirm prompt) and `1` when any registration failed. Re-run it after `ollama pull`. New models show up in Open WebUI as `ollama/<name>`. Pull the model into Ollama first, and have the stack running so `https://litellm.localhost` answers.

    - Error counts by container over the selected range
    - Raw error stream with a search box for narrowing (timeout, refused, 401)
    - Collapsed warning-rate row

12. **container-resources-dashboard.json** - Per-container Docker stats (`monitoring` profile)
    - CPU, memory, network, disk, restarts, PIDs, and uptime
    - Container logs for the selected container

13. **vllm-nodes-dashboard.json** - Remote compute nodes (templated by the `vllm_compute` role)

Each per-service dashboard ends with a logs widget reading its container's stdout/stderr from Loki: LiteLLM, Open WebUI, PostgreSQL, Traefik, and the OTel Collector. Keycloak Authentication has its own Keycloak and keycloak-backup log panels.

Deleted dashboards: `logs_dashboard.json` (dead demo datasource uid), `metrics_dashboard.json` (duplicate of Node Exporter), `stack-logs-dashboard.json` (replaced by the per-dashboard logs widgets), and the community Keycloak capacity-planning and troubleshooting dashboards (built for Kubernetes; their working panels moved into `keycloak-dashboard.json`).

Traefik v3.7 only emits `traefik_entrypoint_*` request metrics when the entrypoint sets `observability.metrics: true`. The `web` and `websecure` entrypoints do. The internal `traefik` entrypoint stays off. Node dashboards default to job `openwebui-stack/node` and instance `node-exporter:9100`. Open WebUI and LiteLLM panels use their OTel HTTP series (`http_server_requests_total`, `http_server_duration_milliseconds_bucket`). Keycloak panels use job `openwebui-stack/keycloak`. HTTP URIs are templates such as `/realms/{realm}/protocol/{protocol}/auth`, so match the braces literally. User events use `keycloak_user_events_total` with lowercase `event` (`login`, not `LOGIN`) and an `error` label that is empty on success. Password checks use `keycloak_credentials_password_hashing_validations_total`.

Job labels: the collector's `resource` processor moves `service.namespace` out of the `job` label (into `stack_namespace`), so scraped series carry plain job names (`keycloak`, `litellm`, `remote-node`) that dashboards and alert rules select directly. LiteLLM's prometheus metrics arrive with OTel-translated names: the `_metric_` infix is dropped (`litellm_proxy_total_requests_metric_total` becomes `litellm_proxy_requests_metric_total`), so use `litellm_proxy_requests_metric_total`, `litellm_tokens_metric_total`, and `litellm_request_total_latency_metric_bucket`. Qdrant's `/metrics` requires the API key; the `qdrant` scrape job sends it as a Bearer token from `QDRANT_API_KEY` (exported to the collector by the compose service).

Chatterbox does not expose Prometheus. With `--profile monitoring`, `json-exporter` reads `/status`, `/status/statistics`, `/memory`, `/memory/config`, `/health`, `/voices`, `/languages`, and `/config`, and the collector scrapes those series. CUDA series are missing on the CPU profile. The compose logging driver is `local`, so there is no json-file log to tail. Grafana Alloy (`loki.source.docker`) reads every container through the Docker API and pushes to Loki with `service_name`, `container_name`, `stream`, and `container` labels set from the container name (and stdout/stderr for `stream`), so log and metric queries filter identically: `{container_name=~".*keycloak.*"}` or `{service_name=~".*keycloak"}` both work. The `stream` label is applied through the source's `relabel_rules` (sharing `discovery.relabel.containers.rules`), because `loki.source.docker` sets `__meta_docker_container_log_stream` per entry after discovery relabeling. Traefik logs reach Loki because `traefik/traefik.yml` sets no `filePath` — Traefik writes runtime and access logs to stdout, which Alloy tails. Alloy stores its read positions in the `alloy_data` volume. The collector still reads `/var/run/docker.sock` for Docker engine stats. Both run as root and join group `DOCKER_GID` (default `999`). Set `DOCKER_GID` from `getent group docker` when that group id differs. App logs that already use OTLP (Open WebUI, LiteLLM, Keycloak) are still exported as well. A backup run prints `keycloak_backup_success 1` or `keycloak_backup_success 0`. The Keycloak dashboard counts those lines. The backup container only exists while `docker compose --profile backup up keycloak-backup` is running.

### Profiles in Pyroscope

The `otel-lgtm` image also runs Pyroscope (continuous profiling) on port 4040. The Grafana `pyroscope` datasource is provisioned in `grafana/provisioning/datasources/datasources.yml`; access it via Grafana → Explore → Pyroscope. Profiles only appear for services that send profiling data (the OTel SDK/eBPF auto-instrumentation does not currently forward profiles in this stack).

### Alerting

Alert rules are provisioned from `grafana/provisioning/alerting/` (`comprehensive-alerts.yml`, `keycloak-alerts.yml`, `alert-rules.yml`) into the Alerts folder: service health, Keycloak SLOs, application errors, system metrics, and GPU temperature.

Service-down rules use `max(up{job="..."}) == 0 or absent(up{job="..."})` with `noDataState: OK`: the `or absent()` arm catches a vanished scrape target (including a dead collector), while a healthy service returns an empty result and stays inactive. Open WebUI pushes metrics via OTLP instead of being scraped, so it has no `up` series; its rule watches `absent(container_memory_usage_total_bytes{container_name=~".*open-webui.*"})` from the collector's docker_stats receiver instead.

Discord notifications: `discord-contactpoints.yml` and `notification-policies.yml` provision the contact point and root policy. The webhook URL interpolates from `GRAFANA_DISCORD_WEBHOOK_URL`, which the `lgtm` compose service passes from the deployed `.env` (rendered from `grafana_discord_webhook_url` in the ansible vault). Grafana validates the Discord receiver at startup and exits fatally if the URL is empty, so both files are renamed to `.disabled` until the vault value exists. To enable:

```bash
# 1. Set the webhook URL (Discord: Server Settings -> Integrations -> Webhooks)
#    in ansible/group_vars/all/vault.local.yml:
#    grafana_discord_webhook_url: "https://discord.com/api/webhooks/..."

# 2. Re-render .env (cd ansible && ansible-playbook playbooks/site.yml), or set
#    GRAFANA_DISCORD_WEBHOOK_URL in the deployed .env directly

# 3. Re-enable provisioning and restart
mv grafana/provisioning/alerting/discord-contactpoints.yml.disabled grafana/provisioning/alerting/discord-contactpoints.yml
mv grafana/provisioning/alerting/notification-policies.yml.disabled grafana/provisioning/alerting/notification-policies.yml
docker compose restart lgtm

# 4. Send a test notification (Grafana UI: Alerting -> Contact points -> Discord
#    -> Test, or via the API)
```
